# Mathematics

**Phase 1 audit — mathematical model of this Library**

This document describes the **upstream v3 algorithm** used by [tdjsnelling/babel](https://github.com/tdjsnelling/babel). Unless a deliberate, documented break is approved, Tony's Library preserves this model bit-for-bit for coordinate ↔ content mapping.

---

## 1. Alphabet and dimensions

| Symbol | Value | Meaning |
| --- | --- | --- |
| `ALPHA` | `abcdefghijklmnopqrstuvwxyz.,!?- ` | 32 orthographic symbols |
| `BASE32_ALPHA` | `0123456789abcdefghijklmnopqrstuv` | Digit alphabet for base-32 integers |
| Walls / room | 4 | Hexagon sides with shelves |
| Shelves / wall | 5 | |
| Books / shelf | 32 | |
| Pages / book | 410 | |
| Lines / page | 40 | |
| Chars / line | 80 | |
| `PAGE_LENGTH` | 3,200 | `40 × 80` |
| `BOOK_LENGTH` | 1,312,000 | `410 × 3,200` |

Borges described 25 symbols; this implementation uses **32** so content packing aligns with base-32 (v3 design choice — faster encode/decode than v2's base-29).

Total unique books:

```text
|L| = 32^1,312,000
```

Rooms needed if each room holds `4 × 5 × 32 = 640` books:

```text
|R| = ceil(|L| / 640) ≈ 32^1,312,000 / 640
```

Room identifiers are base-32 integers and can approach ~1e6 digits — hence URL hashing.

## 2. Coordinate system

Human identifier:

```text
ROOM . WALL . SHELF . BOOK . PAGE
```

| Field | Domain | Encoding |
| --- | --- | --- |
| `ROOM` | ≥ 1 | Base-32 string (`[0-9a-v]+`) |
| `WALL` | 1…4 | Decimal |
| `SHELF` | 1…5 | Decimal |
| `BOOK` | 1…32 | Decimal |
| `PAGE` | 1…410 | Decimal |

Example from upstream docs: `2q.1.3.16.200`.

### Sequential book index

Pages do **not** enter the book index. For identifier `(room, wall, shelf, book)`:

```text
seq = (room − 1) · (WALLS · SHELVES · BOOKS)
    + (wall − 1) · (SHELVES · BOOKS)
    + (shelf − 1) · BOOKS
    + book
```

with `WALLS·SHELVES·BOOKS = 640`.

Inverse decomposition (used for next/prev and random):

```text
room  = floor((seq − 1) / 640) + 1
rem   = (seq − 1) mod 640
wall  = floor(rem / 160) + 1
rem   = rem mod 160
shelf = floor(rem / 32) + 1
book  = (rem mod 32) + 1
```

`PAGE` is carried alongside when addressing a leaf.

## 3. Constants `N`, `C`, `I`

Stored in the repo root file `numbers` (~3.9 MB), three lines, each a base-32 digit string:

| Constant | Definition |
| --- | --- |
| `N` | Largest `BOOK_LENGTH`-digit base-32 integer = `32^BOOK_LENGTH − 1` (all `v` digits) |
| `C` | Random integer, `0 < C < N`, with `gcd(C, N) = 1` |
| `I` | Modular inverse of `C` modulo `N`: `C · I ≡ 1 (mod N)` |

Generated by `src/utils/gen-constants.ts` (GMP). **Regenerating `numbers` creates a different Library.** This fork must treat the existing `numbers` file as canonical for compatibility mode.

Note: `N = 32^L − 1` is **not** a power of 32. Multiplication modulo `N` still yields a bijection on `{0,…,N−1}` when `gcd(C,N)=1`, but the representable book contents are exactly the base-32 strings of length `L` interpreted as integers in `0…32^L−1`. Values equal to `32^L − 1` (= `N`) are excluded by `% N` landing in `0…N−1`; practical generation pads shorter strings with leading zeros to length `L`. This matches upstream behavior.

## 4. Forward map (index → book content)

```text
contentValue = (seq · C) mod N
```

1. Express `contentValue` in base-32 (digit alphabet `0–9a–v`).
2. Left-pad with `0` to length `BOOK_LENGTH`.
3. Map each digit `d` → `ALPHA[parseInt(d, 32)]`.
4. For a single page `p`, take substring  
   `[(p−1)·PAGE_LENGTH , p·PAGE_LENGTH)`.

Upstream always computes the full book value then slices. A future optimization may extract only the needed digit window via:

```text
pageDigits = floor(contentValue / 32^(BOOK_LENGTH − end)) mod 32^PAGE_LENGTH
```

That optimization must be proven equivalent and tested; it does **not** change the mathematical mapping.

---

## 5. Inverse map (book content → index)

1. Map each character of a length-`BOOK_LENGTH` string through `ALPHA.indexOf` → base-32 digit.
2. Interpret the digit string as integer `contentValue`.
3. `seq = (contentValue · I) mod N`
4. Decompose `seq` → `(room, wall, shelf, book)`; attach requested `page`.

### Search construction (application layer, not pure math)

User text is shorter than a book. Upstream builds a full book then inverts:

| Mode | Construction |
| --- | --- |
| `empty` (default) | Random page filled with query (line-aware), rest of book = random alphabet chars |
| `emptybook` | Query at start (line-aware), remainder spaces |
| `chars` | Query at random offset, rest random chars |
| `words` | Query at random offset, rest popular English words |

Therefore **the same query yields different coordinates across runs** when modes inject randomness. Only `emptybook` with identical padding is deterministic for a fixed query.

Product implication: discovery toys that want stable results (e.g. “Today's Page”) must define a **deterministic padding** (date-seeded PRNG or pure left-pad with spaces) and document it.

## 6. Proof sketch of bijectivity

**Theorem (standard).** If `gcd(C, N) = 1`, then  
`f(x) = (C · x) mod N` is a bijection on `ℤ/Nℤ`, with inverse `f⁻¹(y) = (I · y) mod N`.

Hence every `contentValue ∈ {0,…,N−1}` maps to exactly one `seq`, and every valid `seq` in range maps to exactly one content value. Combined with the coordinate ↔ `seq` encoding (also bijective onto its range), the Library is **total** at the **book** grain: every possible 1,312,000-character string over `ALPHA` that encodes to a value `< N` appears in exactly one book.

References cited upstream:

- Eric Lippert — [A practical use of multiplicative inverses](https://ericlippert.com/2013/11/14/a-practical-use-of-multiplicative-inverses)
- Math StackExchange — multiplication by `k` is bijective mod `n` iff `gcd(k,n)=1`

## 7. Book-level vs page-level libraries

| Model | Unit of uniqueness | Contiguous prose across pages? | Cost |
| --- | --- | --- | --- |
| **This project (v3)** | Entire book | Yes — pages are slices of one book value | Mulmod on ~1.3M-digit numbers |
| libraryofbabel.info / many demos | Single page | No — next page is independent | Mulmod on ~3.2k-digit numbers |

**Recommendation:** Keep book-level uniqueness. It is the distinguishing claim of this codebase (“complete unique books, not only unique pages”). A page-level fast path would be a **different Library** and must not silently replace the default.

Optional future: a separately branded “folio mode” with its own `N_page`, `C_page` — never aliased to the same coordinates.

## 8. Arbitrary-precision backends (investigation)

| Backend | Pros | Cons | Fit |
| --- | --- | --- | --- |
| **Native JS `BigInt`** | Zero deps; browser + Worker + CF Worker + Node; small PWA payload | May be slower than GMP on some mulmod sizes | **Default candidate** |
| **gmp-wasm** | Proven in upstream; strong mul/mod | Large WASM; cold start; CF threading limits; Node/browser glue | Optional accel if benchmarks win |
| Pure WASM custom | Controllable size | Build complexity; must re-verify correctness | Only if BigInt + gmp both fail targets |

Independent public benchmarks (π / big-integer suites) often show **modern Node `BigInt` competitive with or faster than gmp-wasm** depending on operation mix. **We will not assume; Phase 2 must benchmark this repository's actual mulmod + base-32 encode/decode for `BOOK_LENGTH`.**

For offline PWA, native `BigInt` is strongly preferred unless gmp-wasm is dramatically faster *and* cacheable under a few MB.

## 9. Performance characteristics (expected)

Dominant costs:

1. `(a · b) mod N` with ~1.3M-digit operands  
2. Base-32 string encoding of the result (`mpz_to_string` / `BigInt.toString(32)`)  
3. Mapping 1.3M digits → characters (full book / PDF)

Page view still pays (1)+(2) in the current algorithm because the full value is materialized. Optimizing (2) via digit-window extraction is the highest-value compatible performance work.

Search modes that fill the book with random words add large JS string work before the inverse mulmod.

## 10. Required mathematical tests (Phase 2 gate)

### Fast suite (`npm test`)

- Geometry constants
- Coordinate ↔ sequential round-trips (README examples)
- Identifier parse/format / bounds
- Base-32 encode/decode
- Search builder shape + deterministic space-pad

### Heavy suite (`npm run test:heavy`)

Uses `numbers.hex.json` (generate once via `node scripts/convert-numbers-to-hex.mjs`).

1. `C · I ≡ 1 (mod N)`  
2. `1.1.1.1.1` page generation (~5 ms observed)  
3. Deterministic space-padded discovery round-trip (~1.5 s)  
4. emptybook construct → lookup → generate full book (~1 s)

Lock fixtures **against the current `numbers` file** so accidental constant regeneration cannot silently ship.

## 11. What “exists” means

Finding a sentence proves only that the constructed book occupies a coordinate. It does **not** imply:

- semantic significance,
- that the surrounding pages continue the sentence meaningfully (unless search mode forced empty/space padding),
- or that the text is rare (almost all books are noise).

UI copy must preserve this distinction (see product philosophy).
